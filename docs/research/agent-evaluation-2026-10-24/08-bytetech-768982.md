## 2. 文章核心结论

文章的核心不是“用大模型给视频打一个分”，而是把 Agent 产物质量问题拆成可定位、可复核、可回归的工程链路：

1. 沿剧创 Agent 生成链路分层评测：剧本解析 → 角色/场景/道具资产 → 分镜与提示词 → 单分镜生成 → 整集拼接。低质成片可能来自上游解析、资产 Prompt、分镜 Prompt，也可能来自下游生图/生视频模型，因此单一总分无法指导修复。
2. 评测目标从“评分”升级为“分层定位”：机器先跑全量、整理证据、筛出高风险 case；人集中处理边界、主观体验和标准仲裁。
3. 评测不是等同于 LLM-as-Judge：确定性字段、结构、时长、资产 ID、聚合等由 Python 检查；语义覆盖、动作忠实度、状态变化、画面/时序问题由 LLM/VLM 判断；低置信或分歧结果转人工。
4. 以“评估合同”约束评估器：每个评估器只回答一类问题，明确输入、输出、评分规则、覆盖范围和排除项；每轮只改一个变量，目标问题召回与正控样本同时过线后冻结版本。
5. 证据优先：低分结果必须返回问题类型、严重度、原文或候选证据、对齐状态和根因；系统失败、字段映射错误、分镜对齐失败不能直接记成质量 1 分。

## 3. 核心方法拆解

### 3.1 分层对象与参考信息选择

文章把评测对象拆成四类：

| 评测对象 | 主要产物 | 机评要回答的问题 |
| --- | --- | --- |
| 剧本解析 | 集数、角色、场景、道具、结构化 JSON | 剧本是否被正确拆解，基础事实是否完整 |
| 资产 Prompt | 角色、背景、道具的图片生成提示词 | 关键资产是否齐全，身份与属性是否正确，描述能否直接用于生图 |
| 分镜 Prompt | 分镜拆解、镜头提示词、资产引用 | 台词、动作、场景和镜头结构是否忠实且可执行 |
| 图片/视频 | 资产图、单镜视频、整集视频 | 最终画面是否响应 Prompt，并保持角色、空间和叙事连续 |

参考信息按维度选择，而不是强行所有维度都依赖 Gold：

- 无参考评测：只看待评产物，适合输出为空、TODO 占位、字段/格式缺失、图片结构异常、视频模糊/闪烁/崩坏/穿模、Prompt 明确禁用项等。
- 基于输入参考评测：使用原始剧本、生成 Prompt、人物参考图或相邻分镜，适合基本指令遵循、身份一致性、跨镜连续性、A/B 版本偏好。
- Gold 评测：使用人工确认的结构化核心事实，适合分镜 Prompt 的台词/动作/资产忠实度、整集分镜拆分合并与顺序对齐、视频核心剧情完整执行、资产关键身份和剧情属性覆盖。

### 3.2 三分制评分，二值化统计

逐条结果保留三分制，方便解释和 Review：

- 3 分：基本可用。
- 2 分：主线正确但需要人工确认。
- 1 分：核心内容缺失或明显冲突。

统计人机一致率时再二值化：

- 3 分 → “没问题”。
- 1/2 分 → “有问题”。

文章强调只在同一评测单元、同一维度且双方都有有效结果时比较；系统失败、对齐失败和“不可判断”不进入分母，应单独统计；多人标注不一致由复核人仲裁。指标至少同时看：

- 一致率：`(TP + TN) / (TP + TN + FP + FN)`。
- 有问题精确率：`TP / (TP + FP)`，回答“机评扣了，人评是不是也认为有问题”。
- 有问题召回率：`TP / (TP + FN)`，回答“人评有问题，机评有没有扣到”。
- 正控通过率和多次运行稳定性。

### 3.3 评估器优化循环

文章的优化流程是“先定口径，再做优化”：

1. 拆清职责与口径：一个评估器只回答一类问题。例如图片拆为单图质量、设定图一致性、设定还原；视频拆为语义执行和人物身份。字幕、跨镜、音画、运镜等合同外问题不“碰巧锁分”。
2. 一次只改一个变量：每轮只优化一个评估器、处理一类可观察问题，例如完成态、对象、人数、朝向或同脸。
3. 设置停止与冻结条件：目标问题召回与正控样本必须同时过线；分数不涨、正控下降或连续两轮无提升时回退上一成功版本；通过后固定评估器 ID/版本、评测集、Target 快照和字段映射。

### 3.4 评测集与 Target 准备

正式评测前，评测集按维度保存原始输入、参考图、相邻分镜或人工 Gold，并记录项目定位和不可变候选信息；Agent 动态产物由 Target 在实验中读取。

关键实践：

- 分镜 Prompt：评测集以集为单位保存完整人工 Gold 分镜；Target 拉取整集 Agent 分镜；评估器先做顺序约束的语义对齐，再逐镜判分。不按序号硬匹配，允许 1:1、1:N、N:1；对齐失败单独 Review，不计为质量低分。
- 资产 Prompt/完整性：Gold 保存去重后的角色、场景、道具，记录名称、类型、来源剧本、必备属性、禁用项、是否必须生成；缺资产属于覆盖或链路问题，不直接记为 Prompt 质量 1 分。
- 资产图片：固定资产 ID、图片候选及版本/哈希；不能运行时选择“最新图”；Prompt 与图片必须能证明同源。缺资产、缺图、媒体不可用和图片质量问题分别统计。
- 单镜视频：技术质量可直接评估；动作、台词和身份评测需使用生成 Prompt、人物参考图或 Gold；视频与生成 Prompt 必须来自同一候选；无法可靠对齐或候选错配时不评分，转人工检查。
- 数据集划分：校准/挑战集用于优化规则，独立测试集用于验收泛化效果，正式回归集固定版本后用于版本比较；不能根据正式集结果逐条补规则。

### 3.5 Fornax 工程流程

文章把 Fornax 主链路总结为：

`准备评测集 → 连接真实 Target → 配置评估器 → 提交实验 → 查看逐条与聚合结果 → 通过 Trace 定位失败`

核心对象：

- Eval-set：按维度保存原始输入、参考信息或人工 Gold，并记录脚本定位信息和评测元数据。
- Target：从剧创平台项目拉取真实分镜或资产产物。
- Evaluator：Python 检查 + LLM 语义质量判断。
- Experiment：绑定评测集、Target、评估器和字段映射。
- Report/Trace：保存逐条结果、聚合指标和失败证据。

文章选择 Fornax 的原因是当前处于评估器密集迭代和真实 Target 验证阶段，Fornax 配置简单、实验与 Trace 回查方便；ByteVal 更适合后续稳定流程编排与平台化运营。

### 3.6 两个工程问题与解决

Target 取数模式：

- `existing_project`：已有平台项目，只需提供 URL 写入评测集即可评测；适合版本对比与固定回归，读已有 stable 项目的 Agent 输出；关键在协议兼容与环境健康检查。
- `auto_create_project`：没有项目，需要从 0 在剧创平台生成项目；适合新剧本冒烟与新样本接入；关键机制是用剧本 blob、team、Agent 版本和生成配置哈希出 `project_reuse_key`，避免重复建项。

分镜对齐与执行优化：

- 问题：Gold 与 Agent 独立决定分镜边界，一条长台词可能被 Agent 拆成多镜，相邻动作也可能被合成一镜；一旦发生拆分/合并，按“Gold 第 N 镜 = Agent 第 N 镜”会持续错位。
- 方案：分镜提示词采用“集级批处理、分镜级判分”。评测集中一集只保留一条数据，Gold 包含完整分镜序列；Target 只调用一次短剧平台，返回完整 Agent 分镜序列；最终仍回答每条分镜 Prompt 好不好。
- 效果：以 11 集、131 条 Gold 分镜为例，Fornax item、Target 调用和评估器调用均从 131 次降为 11 次，调用量减少约 92%，减少任务调度、网络请求、长上下文推理和失败重试耗时。

## 4. 关键能力、指标与案例

### 4.1 V1.6 实践数据

实践对象为短剧 V1.6 真实 stable 项目。整体流程：

`锁定 Gold 与评测合同 → 真实 Target 小样本冒烟验证 → 正式实验 → 下载行级证据与汇总结果 → 人工复核并回流校准`

关键数据：

- 分镜 Prompt：覆盖 10 个真实项目；80 条抽样人机一致率 98.8%；可用于稳定回归和问题定位。文章也提醒，该一致率主要说明回归稳定性，不单独代表问题召回能力。
- 资产 Prompt/图片：覆盖 10 个项目；图片正式可比样本 80 条，一致 69/80（86.3%），问题精确率 90.9%，召回率 69.0%；P0 单图质量、设定图一致性、设定还原度评估器分别冻结为 0.0.12 / 0.0.16 / 0.0.5。
- 视频：10 个剧本、97 条人标样本完成校准；正式覆盖 9 个剧本、109 镜；质量与身份评估器分别冻结为 0.0.14 / 0.0.10；正式一致率约 70%，问题精确率 79%，召回率 65%。

优化效果：

- 图片校准集同组对比：一致率 75.0% → 82.5%，问题召回率 50.0% → 61.8%。
- 视频校准集同组对比：相同 8 部样本中误伤 23 条 → 8 条，问题精确率 64% → 83%；独立正式集 9 部正式结果一致率约 70%。

### 4.2 当前能力成熟度

- 稳定回归可用：分镜 Prompt。维度包括结构完整性、台词忠实度、资产映射、动作忠实度、整集语义对齐、拆分合并、顺序、台词/事件增删改、问题归因。
- 高风险初筛可用：资产 Prompt、资产图片、单镜视频。可用于问题定位和人评前置，但复杂边界仍需人工复核。
- 校准/流程建设中：人机编排、在线触发、自动建任务、完成回调、更多评测环节 skill、跨分镜一致性评估。

### 4.3 可召回问题示例

- 分镜 Prompt 质量问题：台词/OS 漏写、说话人错误、角色/场景/道具漏引或资产映射错误、镜头结构缺失、动作主体/对象/方向/顺序/结果不忠实、拆分合并和顺序错位。示例：`彪悍新娘·第3镜` 中 Gold 要求围观村民哄笑，Agent 漏写，机评动作忠实度 1/3。
- 资产 Prompt 质量问题：关键资产未生成、空内容/TODO、身份错误、关键视觉属性不足、时代题材或风格冲突、描述不足以直接生图。示例：`彪悍新娘·许满月` Prompt 漏八十年代农村与闪回便服，属性 1/3、风格 2/3。
- 图片结构/设定/场景问题：寝具被生成成衣服、群像同脸、公司走廊俯视图变成“深盒子”等。
- 视频语义执行问题：核心动作未完成、完成态被相近动作替代、对象/人数/落点/应答方向错误、同镜内时序矛盾。
- 视频人物身份问题：具名角色复制、身份互换、未命名同脸。示例：`爱丁堡·第15镜` 出现两个相同男一背影，身份评估器成功召回。

### 4.4 暂不能稳定自动决策与合同外问题

暂不能稳定自动决策：

- 复杂空间理解：多视图或空间关系冲突，模型容易补全为合理空间，召回不稳定。
- 低可比身份判断：侧脸、远景、遮挡场景证据不足，容易误伤。
- 过细字面对齐：如粮袋数量、昼夜、屏幕文字、拖鞋配对等，人评可接受时机器可能判严。

当前评估合同不纳入：

- 主观审美和氛围，如“角色不够帅”“氛围太荒凉”。
- 单镜语义评估器外维度，如字幕、音画配合、运镜、跨镜连续性；这些应由独立评估器或技术质量能力承接。

## 6. 可落地候选优化

### 6.1 为本地评测结果引入“评估合同”Schema

- 价值：把当前 outcome/evaluation/optimization 的输出口径固化下来，明确每类本地评估的输入、输出、覆盖范围、排除项、无效状态、证据要求和严重度。可直接吸收文章的“合同外问题不碰巧锁分”和“系统失败不记质量低分”原则。
- 成本：中。需要扩展 `AnalysisEvaluation` / `OptimizationSuggestion` 或新增 `EvaluationFinding`，并调整 UI 展示与测试。
- 风险：Schema 过早固化可能限制后续维度；分类过细会增加使用成本。
- 验证：为每类 finding 增加单测：同一证据能稳定映射到同一 issue_type/severity；缺证据、来源未记录、投影 unsupported、验证缺失分别进入 invalid/unknown/out-of-scope，而不是 bad。

### 6.2 建立小型人标 Gold/Benchmark 轨迹集

- 价值：让本地规则和诊断 skill 从“看起来合理”变成“可量化回归”。可先选 30～50 条脱敏真实会话，标注最终目标、完成度、验证是否充分、未恢复错误、重复/绕路/效率问题、是否应给优化建议。
- 成本：中到高。需要人工标注、脱敏审查和 fixture 管理。
- 风险：真实会话可能含敏感信息；样本偏差会导致规则过拟合。
- 验证：按文章方法拆成校准/挑战/独立测试/正式回归集；每次调整本地评测规则时输出一致率、问题精确率、问题召回率、正控通过率和稳定性，不允许只报总体一致率。

### 6.3 将现有 good/warning/bad/unknown 映射到三分制 + 二值指标

- 价值：保留当前 UI 语义，同时为离线评测提供统一统计口径。建议：`good=3`，`warning=2`，`bad=1`，`unknown/invalid/out-of-scope` 单独统计不入二值分母。
- 成本：低到中。主要是离线 runner 和报告层改造，不必立即改变用户可见文案。
- 风险：warning 的含义在不同维度间可能不一致；二值化可能丢失解释信息。
- 验证：在 Gold/Benchmark 上计算 TP/FP/FN/TN；检查 `unknown` 不进入分母；抽样 Review 二值化是否符合人工直觉。

### 6.4 增加“问题案例库”和低置信 Review 回流

- 价值：文章强调 Review 结论持续回流 Gold 与规则。Agent Trajectory 可把典型误判、漏判、边界样本沉淀为本地 `casebook`，包含来源、脱敏证据、预期判断、实际判断、根因和修复建议。
- 成本：中。需要存储格式、脱敏、导入/导出和 UI/CLI 入口。
- 风险：如果写入真实会话摘要，需严格隐私边界；案例库可能与代码演进不同步。
- 验证：新增一个 case 后，离线 runner 能复现原问题；修复后 case 状态从 fail 变 pass；删除/修改 case 有审计记录。

### 6.5 给本地规则和诊断 Skill 加版本冻结与对照报告

- 价值：文章中评估器 ID/版本、评测集、Target 快照、字段映射冻结是可回归的关键。项目已有 facts hash、source fingerprint 和冻结快照，可扩展为 `analysisRulesVersion`、`diagnosisSkillVersion`、`factsSchemaVersion`、`benchmarkVersion`。
- 成本：中。需要在分析结果、快照、报告和测试 fixture 中增加版本元数据。
- 风险：版本维度过多会增加维护负担；旧快照兼容需处理。
- 验证：同一冻结快照用两个规则版本跑出对照报告，展示新增召回、修复误伤、退化项和未变化项。

### 6.6 把“整集批处理”思想迁移为“会话级/轮次级先对齐，再问题级输出”

- 价值：文章用整集批处理解决分镜错位和重复调用。Agent Trajectory 面对的是跨轮次目标演化、压缩、工具调用和修正链，也应先在会话/轮次级建立目标、阶段和证据对齐，再输出步骤级问题。
- 成本：低到中。项目已有 `turn + step` 聚合和 summary facts，可优先作为规则约束和回归检查。
- 风险：过度聚合可能掩盖单条高风险工具调用；需保留 record-level evidence。
- 验证：对长会话基准比较新旧分析耗时、token/facts 大小、重复建议数量和证据定位准确率；确保高风险 record 仍可定位。

### 6.7 为“合同外/暂不稳定自动决策”增加显式 UI 标识

- 价值：避免把主观审美、证据不足、外部系统不可见、来源未记录等问题误判为模型失败。当前项目已经谨慎表达，但可以进一步让用户看到“为什么不自动判定”。
- 成本：低。可先在本地评测和优化建议中增加 limitation/outOfScopeReason 展示。
- 风险：过多 unknown 可能降低用户信任；需要给出最小补证步骤。
- 验证：构造来源未记录、缺验证、用户线下处理、外部 API 无响应等 fixture，确认 UI 给出 unknown/需补证，而不是 bad。

### 6.8 做版本回归报告，而不只是单会话诊断

- 价值：文章最终目标是支撑“这一版到底有没有变好”。Agent Trajectory 可在同一 benchmark 会话集上比较两个提交/两个规则版本/两个模型版本，输出新增问题、修复问题、未变化问题和指标变化。
- 成本：中。需要离线 runner、报告格式和 benchmark 选择。
- 风险：不同来源或不同会话版本不可比；需要固定输入和快照。
- 验证：用同一冻结 benchmark 连跑两版，报告能稳定复现；对故意引入的规则退化能显示召回下降或误伤上升。

## 7. 不建议照搬的部分

- 不建议直接接入 Fornax/ByteVal 作为当前项目核心依赖。Agent Trajectory 的定位是本地、只读、多来源轨迹查看器；引入内部平台会破坏轻量分发和离线/本地隐私边界。
- 不建议照搬剧创 AIGC 的图像/视频 VLM/OCR/人脸检测评估器。当前项目关注 Agent 行为轨迹，除非未来分析多模态 Agent 产物，否则视觉评估器不是第一优先级。
- 不建议把三分制文案原样替换当前 UI。更合理做法是在离线评测和基准报告中映射三分制，在用户界面继续保留“good/warning/bad/unknown”等符合轨迹分析语境的标签。
- 不建议自动创建外部项目、自动触发人工平台或报告推送。文章中的 `auto_create_project`、MM 人工评测平台和团队推送属于剧创平台工作流；当前项目应先做本地 casebook/benchmark，不扩大外部副作用。
- 不建议把“问题精确率/召回率”用于没有人标 Gold 的线上单会话。没有 Gold 时只能展示本地证据、置信度和限制，不能假装有正式指标。
- 不建议把主观质量、审美、团队流程偏好等纳入自动扣分。应显式标记为人工 Review 或项目规则自定义项。

## 9. 最小落地顺序建议

1. 先做评估合同 Schema 和 invalid/out-of-scope 分类，不需要新平台，也不需要人标数据。
2. 再抽取 30～50 条脱敏 benchmark 会话，建立人标 Gold 和离线 runner。
3. 在 benchmark 上引入三分制映射、二值 TP/FP/FN/TN 和正控/稳定性检查。
4. 最后做规则版本对照报告和 casebook 回流，形成“badcase 归因 → 规则/skill 优化 → 回归”的闭环。

这个顺序能最大化复用当前已有的冻结快照、事实包、证据 ID、优化建议和诊断 Skill 机制，同时避免过早引入外部平台或人工流程副作用。

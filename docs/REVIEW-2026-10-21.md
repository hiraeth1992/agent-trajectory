# Agent Trajectory 独立复核（2026-10-21）

复核对象：`projects/agent-trajectory`（v0.1.0，约 2.5k 行 TS/TSX，三来源只读轨迹查看器）。
方法：通读全部源码 + 跑测试/构建/audit + 使用脱敏的代表性数据做端到端计时与
CPU profile + 对可疑热点做微基准和补丁验证。

基线：`npm test` 82 passed / 4.57s，`npm run build` 通过，`npm audit` 0 漏洞。功能可用，安全边界设计扎实（Host 校验、opaque ID、readOnly + 绑定参数、schema fail-closed、双重有界 LRU、revision delta 协议）。

但 `docs/OPTIMIZATION.md` 把 P0–P2 全部标成 ✅，与实测不符：**当前最大性能热点不是"轮询重扫目录"，而是一条正则和主线程投影**。下面按严重程度排列，每条都带可复现证据。

---

## P0-1　`redactSensitiveString` 里的 URL 凭据正则退化为 O(n²)，吃掉 92% 的冷加载时间

位置：`src/projector-utils.ts:51-54`

```ts
/([a-z][a-z\d+.-]*:\/\/)([^/\s:@]+):([^/\s@]+)@/gi
```

`[a-z][a-z\d+.-]*` 没有上界。当正文里出现较长的连续 `[a-z0-9+.-]` 字符串时，
正则引擎要在每个起点回退整段，代价是 O(n·run)。

实测（7.14 MB Codex rollout，2,476 行 / 1,021 条记录）：

| 阶段 | 耗时 |
| --- | ---: |
| 读文件 + `JSON.parse` | 67 ms |
| `projectCodexTrajectory` | **5,605 ms** |
| transport + SHA-256 | 19 ms |

`node --cpu-prof` 聚合 self time：**5,430 ms / 5,874 ms（92%）全部落在这一条 RegExp 上**（其余正则合计 <100 ms）。

HTTP 端到端更能说明影响面：全新进程冷加载该会话 **5.71 s**，期间并发 `/api/health` 被阻塞 **5.22 s**——整个服务（三个来源、所有会话、所有 SSE 连接）一起冻结。单条 65 KB 字符串就贡献 1,268 ms。

单点微基准（同一份 5.62 MB 字符串语料）：

```text
current (无上界)              2175 ms
scheme<=32                    125 ms
scheme<=32 + lookbehind        25 ms   ← 87x，脱敏结果完全一致
```

建议补丁（保持语义，仅限定量词）：

```ts
.replace(
  /(?<![\w+.-])([a-z][a-z\d+.-]{1,32}:\/\/)[^/\s:@]{1,256}:[^/\s@]{1,256}@/gi,
  '$1<redacted>@',
)
```

已用该补丁实测：投影 5,605 ms → **215 ms**，冷加载 5.71 s → **0.46 s**，并发 health 最大阻塞 5.22 s → **16 ms**。验证后已还原代码，未落盘改动。

> 附带风险：这条路径对本地内容也不设防。任何一条把大段小写文本（base64、minified JS、锁文件）写进工具输出的会话，都会让服务不可用数秒。这既是性能问题，也是本地 DoS 面。

## P0-2　投影全程在 HTTP 主线程，且每次变化都全量重投

- `OPTIMIZATION.md` 只把 ZCode 的 SQLite 查询搬进了 Worker（`server/sources/zcode-worker.ts`），但 **JSONL 解析、三个 projector、`redactSensitive` 深拷贝、transport 构造、两份 `JSON.stringify`、SHA-256 仍在主线程**。
- `DshSource.load` / `CodexSource.load` 每次指纹变化都从头 `project*Trajectory(全部事件)`（`server/sources/codex.ts:334-420`、`server/sources/dsh.ts:278-382`）。活跃会话每 1.5 s 追一次 → 单会话生命周期内 O(n²)。
- 修掉 P0-1 后 7 MB 会话冷加载仍需 ~0.46 s；按 10 万事件量级外推是数秒级，与 `performance.test.ts` 的宽松阈值不矛盾（见 P2-1）。

建议：
1. 把 parse+project 放进 Worker 池（复用现有 `zcode-worker` 模式），主线程只做缓存与序列化；
2. 增量投影：保留已投影记录表，只对追加的 seq 区间重投，按 record id 做 upsert（协议已经支持 upsert/delete，服务端还没利用）；
3. 至少在 `load()` 里把「指纹 → 一次 stat」合并，避免 `list()`/`fingerprint()`/`load()` 各扫一遍目录（见 P1-3）。

## P0-3　每次请求对同一份数据序列化 2–3 遍，空变更也要 30–55 ms

`server/api.ts:170-204` 的 `detailResponse` 每次请求都：

1. `transportDetail()` → 逐条 `boundedPreview()`，内部对每个 `input/output` 做一次 `JSON.stringify` 只为量字节（`api.ts:109-120`）；
2. `JSON.stringify(current)` 算 revision；
3. `sendJson()` 再 `JSON.stringify` 一次响应体。

实测（2.39 MB payload）：`boundedPreview` 7 ms + hash 遍 9 ms + SHA-256 3 ms + 响应体 8 ms = **28 ms/请求**；真机 warm GET 稳定 **54–57 ms**。SSE 每次 `update` 都会触发一次；`?revision=` 未命中时返回 44 KB 的 `upserts: []`，仍然付全部成本。

建议：在 detail cache 条目上附带 `{ revision, transport, serializedBody }`；请求 revision 与缓存 revision 相同时直接回 `{kind:'delta', upserts:[], removedIds:[], recordOrder}` 并跳过 transport 重建与序列化。`boundedPreview` 改用 `Buffer.byteLength(serialized)` 之外的路径，或对已序列化过的字段缓存长度。

## P1-1　ZCode 指纹是「整库」的，空闲会话也在每 1.5 s 触发刷新

`server/sources/zcode.ts:297-304`：

```ts
return Promise.all([
  fileSignature(this.database),
  fileSignature(`${this.database}-wal`),
  fileSignature(`${this.database}-shm`),
]).then(signatures => signatures.join(':'))
```

`db.sqlite-wal` 的 mtime 只要 ZCode 进程有任意写入就会变。实测对一个**没有变化**的 ZCode 会话订阅 `/api/stream` 12 秒：

```text
8 × event: update          ← 基本每个 tick 都发
data: {"version":"...:1792580709305.8308..."} → "...:1792580710306.3035..." → "...:1792580712308.2798..."
```

即 UI 开着 ZCode 会话时，前端每 1.5 s 全量刷新一次详情（服务端 30–55 ms + 客户端整树重渲染，见 P1-2），而用户看到的画面没有任何变化。这与 README「只刷新当前来源和会话的已落盘数据」不符。

建议：指纹下沉到会话级，一次索引查询即可：

```sql
SELECT s.time_updated,
       COALESCE(MAX(m.time_updated), 0),
       COALESCE(MAX(p.time_updated), 0)
FROM session s
LEFT JOIN message m ON m.session_id = s.id
LEFT JOIN part p   ON p.session_id = s.id
WHERE s.id = ?
```

（或用 `session.time_updated` + 行数）；代价 ~1 ms，且只在真正相关时触发。

## P1-2　前端：SSE 触发的刷新会中止在途请求，大会话可能活锁

`src/App.tsx:146-149`：`loadDetail()` 一进来就 `detailRequest.current?.abort()`。当一次详情加载超过 1.5 s（大会话 + P0-1/P0-2 的现状完全可能）且会话在持续写入时，每个 `update` 都会掐掉上一个请求，**加载永远无法完成**——恰好是「看一个正在跑的 agent」这个主场景。

建议：改成「在途时只记一个 pending 标志，落地后再拉一次」，而不是 abort 重启；服务端也应对已断开的响应做早停（目前 `response.destroyed` 只影响 SSE 写入，HTTP 详情仍会算完）。

另：`hydrateRecord()`（`App.tsx:64-69`）对每条记录重算 `recordSearchText`，而 delta 为 0 upsert 时也会整表 `applyDetailDelta` 重建数组，进而让 `Timeline`/`VirtualLedger` 全量重渲染（两者都没有 `React.memo`，`Timeline` 还逐条渲染绝对定位按钮、无虚拟化）。

## P1-3　服务端仍给每条记录算 `searchText`，然后丢掉

`src/projector-utils.ts:96-102` 的 `projectedRecord()` 对每条记录调用 `recordSearchText()`（`jsonText` 全量序列化 + 6 条正则 + `.slice(0, 16KB).toLowerCase()`），随后 `server/api.ts:125` 的 `transportRecord()` 立刻把 `searchText` 解构丢弃；客户端 `App.tsx:67` 自己重算。

已验证：`searchText` 在 HTTP 路径上无人消费（只在 `tests/*` 和客户端自算处出现）。建议在服务端投影时跳过（加 `includeSearchText` 选项，仅供离线导出/测试使用），可省掉一次全量序列化 + 一轮正则。

同源问题：**每条记录被脱敏 2–3 次**——`acceptedRaw()` 先对 payload 脱敏（`codex.ts:160-172`），`projectedRecord()` 再对整条记录（含 `raw`）深拷贝+脱敏，`recordSearchText()` 又对其中字段再来一轮。`raw` 只在审计导出和 `/records/:id/raw` 用，建议改为在传输/导出边界按需脱敏，投影阶段保留引用。

## P1-4　Codex 加载路径重复 I/O（已修复）

首次 `list()` 现在会建立共享的页面与目录索引，按 session 聚合所有分页。后续稳定的 SSE `fingerprint()` 轮询只检查已知目录、当前会话页面和 `session_index.jsonl` 的文件状态，不再重新遍历目录、打开已索引 rollout 的首行，也不会重复读取未变化的 `session_index.jsonl`。

目录签名变化时只扫描发生变化的目录，并且只读取新增 rollout 的首行；因此后来出现在新日期目录中的续页也能被已打开会话实时发现。首行暂时为空或写入不完整的 rollout 会进入待重试集合，在文件状态变化后重新解析。

回归测试已覆盖跨日期续页、稳定轮询零 header/index read，以及残缺首行恢复。
索引建立后的稳定 `fingerprint()` 测试验证为 0 次 `open`、0 次 `readFile`、0 次
`readdir`。

余项：`load()` 路径仍有少量可进一步合并的重复 `stat`，但原 P1-4 所描述的实时轮询全目录扫描与全量 index 重读问题已经消除。

## P2-1　性能门禁测不到真正的热点

> 状态更新：已解决。当前门禁分别覆盖 10 万事件复杂度、三来源匿名生产形状的
> parse/project、共享 Worker 往返，以及 200 条 64 KiB 工具输出的脱敏热点，并为每个
> 阶段设置独立上界。以下内容保留为修复前的评审记录。

`tests/performance.test.ts:15-21` 构造 10 万个**完全相同的 `turn/start`** 事件，无正文、无工具输出、无敏感字符串，且只覆盖 DSH 的 parser+projector：

- 没有长字符串 → 抓不到 P0-1 的 5.4 s 正则；
- 没有 Codex/ZCode 投影开销量化 → 覆盖不到实际最慢的来源；
- 阈值 10 s 过宽（实测 215 ms 与 5,605 ms 都能"通过"）；
- `projectTrajectory` 里 `turns.map(turn => records.filter(r => r.turn === turn))` 是 O(轮次×记录)，该用例里 `records` 为空，正好躲过。

建议：加一个「真实形状」基准（含 64 KB 级工具输出、含 `://` 与长小写串、三来源各一份），断言**单阶段**耗时（parse / project / transport / hash 分别设阈），并在 CI 里对比基线。

## P2-2　`verify:real-sources` 不可复核

> 状态更新：已解决。CLI 现在支持 `--dsh-session`、`--codex-session` 和
> `--zcode-session`，三者必须同时提供；证据记录 `selectionMode: "explicit"` 和各来源
> session ID 的 SHA-256，不写原始 ID、路径或正文。覆盖已有证据文件时也会收紧权限为
> `0600`。以下内容保留为修复前的评审记录。

`scripts/verify-real-sources.ts:107-117` 的 `readLatest()` 取 `source.list()[0]`，即**按 mtime 最新 = 正在被写入的那个会话**。所以：

- 重跑必然得到不同 SHA-256，"同一份输入可复核"无法成立；
- 由可变真实会话生成的证据会随会话继续写入或投影逻辑变化而失效，不应提交到公开仓库。

建议：`--session <id>` 显式指定，或固定 fixture；把期望摘要写进断言，让脚本可当回归用。

## 建议的落地顺序

1. **一行修复 P0-1**（正则加上界）——收益最大、风险最低，冷加载 5.71 s → 0.46 s。
2. **P0-3 缓存序列化结果** —— 空变更请求从 28–55 ms 降到 ~0，直接放大 P1-1 的收益。
3. **P1-1 会话级 ZCode 指纹** —— 消除"空闲也在刷"的观感问题。
4. **P1-2 前端不发 abort 风暴** —— 保证大会话在实时刷新下也能加载完成。
5. **P1-3 去掉重复脱敏**；**P1-4 重复 I/O 已修复** —— 继续降低冷加载开销和内存占用。
6. **P0-2 投影进 Worker + 增量投影** —— 结构性改造，放在前面几项之后再评估。
7. **P2-1 / P2-2 门禁补强** —— 让上面这些不回退。

> 说明：本复核未改动任何源码；P0-1 的补丁与所有数字均来自临时应用后的实测，验证完已还原（`src/projector-utils.ts` 与原件逐字节一致）。`docs/OPTIMIZATION.md` 的结论建议在本轮修复后按实测重写。
